# 训练项目交付

让交付对象能用明确版本的代码、环境和数据重现已声明的训练能力。交付结论必须能追溯到实际执行版本，不能将“环境能导入”“旧版本跑过”“镜像已上传”合并成“当前交付物全部验收通过”。

## 从当前阶段进入

先读项目规则、用户最新要求和最近证据。识别用户要的是完整推进、某个阶段的补齐，还是只整理文档。已有授权持续有效；只做复盘或文档时不扩展为 GPU 训练、远端环境变更或制品发布，文档提交/上传按已有授权完成。

从现有记录提取以下信息，缺什么补什么，不要求用户重新填写已知信息：

- 交付对象与目标：能启动、正确性、性能、长跑、恢复、可迁移环境分别要求到哪一步。
- 权威源码与发布目标：仓库边界、分支/commit、工作区修改、PR base、同步路径。
- 执行环境：连接身份、宿主机/容器、镜像 digest、GPU 拓扑、共享挂载和可用资源。
- 训练合同：模型/数据版本及语义、精度、batch/累积/并行方式、schedule、计时口径。
- 允许执行的机器、GPU、时间和变更范围，以及仍缺的关键输入。

在用户指定或项目既有的任务记录中维护一张简短验收表：`验收项 | 状态 | 代码/环境/运行ID | 证据 | 未覆盖范围`。状态采用“未执行 / 执行中 / 通过 / 失败 / 不适用”；最后核验时间单独记录。标出唯一的当前状态来源；只有记录维护在本次范围内时才整理 `AGENTS.md` 或迁移历史，单次审计在审计结果中指出状态冲突即可。

## 环境与数据：先确定需要补什么

读取 [环境、安装与镜像交付](references/environment-and-release.md)。先区分**原始基础镜像、当前工作容器、准备发布的镜像**，分别取证，不用当前容器的 `pip freeze` 推断基础镜像已有依赖。

保留已验证的平台 torch/驱动栈，审计上游 requirements、项目元数据和安装脚本的实际解析结果。只补目标训练入口需要的差异；虚拟环境、版本锁定和容器权限遵循项目选择，不把本案例的默认 Python 或 privileged 变成所有项目的要求。

确认数据完整性之外，还要核对任务相关语义，例如文本任务的 tokenizer、标签与 packing，视觉任务的解码与增强，机器人任务的 action/state、坐标系、旋转与归一化。替代数据插件可以用于跑通，但不能据此声称复刻客户训练。确认节点使用同一共享目录后只同步一次；独立副本和容器本地依赖仍须逐节点核验。

## 适配与验证：逐层扩大结论

根据改动风险与已授权目标，依次选择必要层级，不把每次文档修改变成全量训练：

1. 安装/导入和 CLI：确定解释器、实际 import 路径与后端。
2. 设备及关键算子：实际 dtype/shape 的 forward、backward，必要时参数更新对照。
3. 单机短跑：完整训练配置下 loss/梯度有限、步数正确、退出正常。
4. 多机短跑：先验证真实身份的启动通路与通信（SSH 或调度器），再检查所有节点与 rank、GBS 和失败清理。
5. 性能重复与长跑：前者判断稳定收益，后者观察持续推进、资源增长和保存周期。
6. checkpoint 保存/恢复与新环境复现：分别验证恢复语义和交付环境，不由短跑或镜像导入测试代替。

详细结论边界和计时方法见 [验收与性能口径](references/acceptance-and-performance.md)。记录未执行项；用户只要求部分能力时可以交付对应范围，但不能写成全部通过。

适配前先验证真实执行路径。以 Attention 为例，SDPA 是 API，实际后端可能已是 fused flash；外部 flash-attn 是否可用、是否命中、是否更快是三个不同问题。平台适配不机械替换设备名，不吞掉 OOM/数值错误来制造成功。

## 启动与运维：从用户使用位置验收

先复用项目既有入口，确有职责缺口才加包装层。默认值集中且可查，保持用户选择的显式脚本配置或配置文件形式。

多机入口优先一次启动。SSH 启动且启动器支持时，机器表可用 `host slots=N` 简单形式；用户/端口、异构卡数等确有差异时才增加配置。调度器项目沿用其原生资源与启动方式，不额外引入 SSH/hostfile。区分宿主机管理 SSH、容器 SSH、训练 rendezvous 与 RDMA 网络。

从**客户将实际敲命令的目录、容器和用户**验证启动通路。使用 SSH 时验证免密，包括启动器确实会连接的自身节点；host 网络要检查端口冲突，重建容器后验证 SSH host key、服务和认证。控制端能 SSH 到宿主机不等于容器入口可用。

启动器应能预检、生成唯一运行目录、记录节点日志/退出状态，并在节点失败或用户中断时清理该次任务。停止优先按作业 ID、run ID 或独有进程组定位；若脚本按源码目录匹配，先核对该目录是否还有不在停止范围内的作业。写清是否保存 checkpoint，不使用全局 `pkill python`。清理后逐节点核对目标进程及其 GPU 占用；超时或节点不可达时报告未确认停止的范围，不能仅凭停止命令返回宣称资源已释放。扩大到停止整个容器前须确认其内其他工作也在授权范围内。默认日志保留错误和警告，详细通信日志仅用于诊断。

长跑和上传放在执行端可脱离本地会话的机制中，持久记录 run ID、命令、日志、启动时间和退出码。训练启动前从既有授权确定步数或时长预算、结束方式、保存策略和重试范围；未约定自动重试策略时，无人值守任务记录失败而不自动重启，不妨碍授权范围内的诊断与有界修复复跑。重连后先恢复真实状态；重试前确认旧任务已结束或完成清理，使用新 run ID 保留旧证据。检查进度时同时关联进程归属、step 增长和最新日志时间，不能只看 GPU 占用；长跑判定还需检查[观察记录的覆盖范围](references/acceptance-and-performance.md#长跑观察与恢复)。

## 性能优化：保留可解释的收益

先建立同口径基线，再用 Trace/等待时间定位数据、CPU、计算或通信瓶颈。按专项 skill 执行受控实验，保存负结果；不能因为双机慢就只扫通信参数。

单机和多机分别选择配置。channels、padding、workers、prefetch、overlap 等值必须由当前拓扑实测支持；增加 workers 还要核算所有 rank 的 CPU、内存和共享存储压力。变更精度、batch、采样或重计算时同时说明性能合同发生的变化。

接近目标时复跑；没有达到阈值就报告观测结果、波动、已证明/待证明的瓶颈和下一步。单次最快值不是稳定值，一段 Trace 不是硬件极限的证明。

## 代码、镜像与文档收口

PR 按可独立 review/回退的改动拆分，例如平台适配、性能优化、安装/启动体验；不为形式强拆不可独立工作的代码。创建与更新前确认实际 base/head/合入/revert 状态，依赖 PR 明示依赖与合并次序。只给最终 diff 引用匹配的验证，合入或清理后按影响范围复核。

运行所需代码、正确性测试与简短使用说明留在源码；临时探针、机器私有信息和原始性能证据按项目约定保存在实验区。性能 PR 提供简要结果及可访问的证据，不因清理源码就丢失验收依据。公开发布前检查证据是否适合该受众。

准备镜像时使用环境参考中的发布步骤；完成以 registry digest 和验证记录为准，不以 push 已启动为准。代码分支、镜像标签、容器现状和数据版本各自有身份，不能互相替代。

读取 [交付文档模板](references/delivery-template.md)，默认按“环境准备、容器启动、启动训练”组织操作稿；已有交付格式或非容器项目按用户和项目要求调整。给一条推荐复现路径，常量与脚本一致，每段命令标注执行位置；故障排查和完整历史放到附录或证据文档。安装步骤只写该交付环境额外需要的内容。

交付前做一次命令顺序审查，并在约定环境实际复现所需层级。只更新用户指定或项目约定的交付记录；云端最终稿不可读时说明来源限制，不能声称已审阅或擅自覆盖。最终报告列出交付物、已验证范围、未完成项；review 按用户指定渠道提供，已授权提交、上传或创建 PR 时完成该步骤，无此授权时提供本地审查结果。
