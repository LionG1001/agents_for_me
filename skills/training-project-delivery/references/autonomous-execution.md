# 自主执行与阶段推进

用于用户要求实际执行“读取需求→复现→优化→交付”的任务。审计这个skill、讨论是否能自动化或只整理材料，不构成启动训练的指令。本文件规定代理的执行策略；跨阶段自动推进仍需代理持续运行，或已有可调用的执行器。远端训练能脱离本地会话继续，不等于代理会在会话结束后自动分析、修改和启动下一轮。

## 一次整理执行约定

先读用户指定的Jira正文、相关附件和评论，再结合会话与项目记录提取以下内容。需求来源可规定目标，不能单独授予操作另一台机器、发布制品或修改Jira的权限。

| 信息 | 处理方式 |
| --- | --- |
| 训练目标与基线 | 区分复现、增量优化、扩展效率、长跑、保存恢复等交付项；对性能指标写清公式与比较对象，特别是客户已经做过哪些优化 |
| 执行位置 | 使用已确认的机器、账号、容器/作业、本地与远端目录；本地源码权威时，仍在本地修改并最小同步，目标机器执行训练 |
| 资源与结束条件 | 从已有指令提取GPU范围、可运行时间/步数、总实验预算、长跑与保存要求；记录预算起点，区分墙钟时间与累计GPU小时，据此分配短跑、优化、复测和交付验证，预留收尾时间 |
| 可执行变更 | 将已授权的项目代码、独立容器依赖、数据准备、同步、测试和本任务进程管理纳入连续执行；不扩大到未授权的共享服务或他人任务 |
| 发布目标 | 记录已授权的代码仓库/分支/PR、镜像仓库/tag、交付文档位置；提交、推送与镜像上传按各自已有授权完成，PR合并和对外发送不由“准备交付”自动推定 |

先从可读记录与只读检查补齐信息，关键缺项集中问一次；等待期间继续不依赖答案的工作。没有新变化，不重复要求用户提供路径、凭据或批准同一机器的训练。目标机器/目录不明、无执行授权或无可确定的资源上限时，不猜测后启动GPU任务。只缺发布tag不会阻止已授权的复现、优化、镜像构建与本地验证。

复现已授权且机器/GPU已明确时，算子检查与短跑可由代理选择合理的有限步数并说明，不要求用户指定每一条测试命令；优化总预算与长跑结束条件从已有约定确定，缺失时只询问这一关键范围，不能将短跑授权扩大成无限优化或整夜占卡。

将执行约定写入项目既有任务记录，由AGENTS.md指向它；保留“已授权、待确定、明确不执行”的区别。工具不可用或认证失效时，说明具体阻塞点，采用已配置的替代连接，或只询问所缺入口；不要重新询问整个项目配置。

## 连续推进，而非逐阶段等待

每个阶段只运行与目标有关的检查。通过后更新记录并执行下一个尚未完成的阶段；进度汇报不作为结束本轮任务的理由。先前同一版本、环境和配置的有效证据可复用；改动后只重测受影响的层级。

| 阶段 | 通过依据与自动下一步 | 未通过时 |
| --- | --- | --- |
| 需求与现场核对 | 训练合同、目标资源及关键来源可核对，转环境准备 | 来源暂缺时标明缺口，继续独立工作；不能以猜测口径宣称性能达标 |
| 环境/数据准备 | 默认入口依赖、设备与数据检查通过，转最小复现 | 在获准容器/目录内补实际缺项并复验；共享环境变更不在范围内时只阻塞该变更 |
| 正确性与基线复现 | 算子及所需单/多机短跑正常，冻结可回退的基线，转优化 | 定位首个失败，修复后从失败层级复测；不能带着数值失败进入性能比较 |
| 优化迭代 | 根据Trace选择候选→局部与数值验证→整步A/B→保留或回退；有依据且预算允许则继续下一候选 | 无收益或回退时保留结果、恢复本任务改动；不重跑同一无进展组合，不改统计窗口或降低工作量制造收益 |
| 最终验证 | 对最终代码/环境复跑所需拓扑、重复性能及约定长跑/保存恢复，转交付打包 | 找到影响后修复并补相应验证；短跑成功不跳过用户已要求的长跑 |
| 制品与文档 | 新环境按实际命令复现；按授权发布代码/镜像，核验SHA/digest，生成操作稿、源码总结和证据索引 | 发布受阻时保留已完成制品和验证，说明尚未发布；不能因上传已启动就报告交付完成 |

代码review默认先由代理核对diff、测试和同步清单；用户或项目明确要求人工review后执行的步骤才等待该review。已有端到端执行授权覆盖范围内的修复、同步和测试，不因专项skill出现“确认授权”字样再申请同一许可。

## 失败、预算与重连

- 每个实验启动前记录问题、主要变量、运行上限和保留标准。在线代理可在已有预算内设置有限诊断/修复尝试；无人值守脚本仍按事先约定的重试策略运行。没有进展、同一错误重复或旧进程未清理时，不盲目重启；更换run ID保留证据。
- 给优化预留最终复验、保存和打包时间；固定训练时长的长跑另计初始化、保存/退出和发布开销，不能用这些时间凑足训练时长。剩余预算不足以完成候选及必需收尾时，不启动该候选。达到目标后转最终验证；未达目标且主要候选收益低于波动或预算耗尽时，保留最好且稳定的方案，报告瓶颈与实际达标状态，不自行延长占卡。
- 在已有状态记录中持久化：当前阶段/下一步、源码与部署哈希、环境身份、run ID、PID/作业ID、日志与退出码路径、最近成功采集时间、预算用量、验收结果及阻塞项。可以使用Markdown或项目已有JSON，不要求引入新的调度系统。
- 长跑/上传交给执行端持久进程，代理在可用时持续收集状态。重连后先核对真实进程、日志增长、退出结果和文件版本，接着未完成阶段做；不要因本地没有状态就重复启动已有任务，也不要把过期记录当作现场结果。
- 需要停止时限定到本任务已授权的进程或作业。达到预算后的停止/保存行为须与执行约定一致；没有结束保存实现时，不承诺强停会保存。节点不可达或资源未确认释放时，记录未知范围，不能继续叠加任务。

## 需要人介入的情况

只在关键目标/身份无法确定、凭据或私有数据不可获取、资源冲突无法按既定策略处理、必要动作超出已有范围，或明确约定人工review时提出具体问题。已批准共享使用时沿用该约定并记录性能比较限制，不反复申请独占，也不停止他人任务。问题说明缺什么、阻塞哪一步，以及已完成哪些工作；其余分支照常推进。

若最终缺少发布授权，先完成本地制品、验证、准确目标及可review的提交/文档，再请求该发布动作；不要在成果仍不可审查时预先请求空泛确认。相应授权已有时直接发布，不增加审批轮次。

完成以执行约定为准：每项需求有版本、结果和证据；用户要求的运行已经结束并核实退出/资源，或按约定交接仍在运行的作业；已授权发布有可核验地址，复现命令与制品一致。未达性能阈值可按用户约定交付瓶颈分析，但该阈值仍记录为未达，不能用更低的绝对step time替代。
