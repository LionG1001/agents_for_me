# 交付文档模板

用于客户复现稿或最终交付审查。默认采用三部分主结构，按真实项目填充，删除不适用段落；用户已有格式优先，非容器项目将容器部分改为实际执行环境准备。不要把内部探索过程放到主操作路径。下面的 `<…>` 是生成时待替换字段，最终交付不得保留不能执行的占位符。

## 1. 环境准备

开头用一段话说明交付支持的模型、训练拓扑和已验收范围，并标注版本/日期。

| 内容 | 确认值 |
| --- | --- |
| 机器 / GPU / 驱动 | <与验收一致的最低条件或具体环境> |
| 镜像 | <可拉取引用及 digest> |
| 源码 | <仓库、分支用于导航、不可变 commit 用于复现> |
| 模型 / 数据 | <来源、版本或校验信息、容器内目录> |
| 软件栈 | <Python、平台 torch、分布式库等关键版本> |

说清镜像已含什么、还需安装什么。若安装必须进容器执行，写“完成第2部分后，在容器内执行以下一次性步骤”，不要让用户在宿主机先安装 Python 包。每条命令对应明确 cwd、用户和依赖前提。

厂商组件另列来源/校验和；凭据通过组织既有途径提供，不写入文档。镜像已配好时不要混入旧基础镜像重建步骤；需保留时放到独立附录。

镜像引用使用用户确认的基础镜像仓库名及交付 tag，不自行改名。内部 `AGENTS.md` 保存机器与本地/远端目录映射；客户稿只保留该接收方需要的环境信息，不复制开发者连接身份或私有目录。

数据插件有替代、归一化或表示差异时，用一句话说明它影响的验收范围，细节链接到对应说明。

## 2. 容器启动

Docker 项目明确“每台宿主机执行”并给出一条已核验的 `docker run`；调度器项目给出其原生作业/容器入口与资源要求。包含所需 runtime、挂载、工作目录及已验证配置，不臆造设备参数。已有环境如何进入、新建环境如何准备，两条路径分清。

多机只保留必要说明：

- 用户从哪里启动；宿主机管理入口与容器训练入口分别是什么。
- 使用 SSH 启动时，容器用户到所有训练节点的认证前提，必要时包括自身。
- 使用 SSH/host 网络时，对应的端口、服务启动、主机密钥与冲突检查。
- 已约定沿用基础镜像 SSH 身份时写明保留范围并验证认证；已可用的免密不要求重配。
- 源码/模型/数据路径一致；共享存储与节点本地依赖各自的准备范围。

提供一个不占 GPU 的预检命令或明确的连接检查。认证尚未配置时写为前提，不能给出注定失败的“一键启动成功”承诺。

## 3. 启动训练

主路径应尽量做到进入已准备的工作目录后执行一个 bash 命令。使用项目已有脚本名；模板不要求再新增一层脚本。

```bash
cd <容器内源码目录>
bash <单机训练入口>
```

使用 hostfile 的多机入口给出启动器实际支持的机器表，例如：

```text
<节点A地址> slots=<每节点GPU数>
<节点B地址> slots=<每节点GPU数>
```

注明只在控制节点执行一次，由脚本读取 hostfile 启动所有节点，不让用户逐台登录启动训练。如果项目采用调度器原生启动，解释相应命令，不硬套 SSH。

```bash
cd <容器内源码目录>
bash <多机训练入口>
```

正文只再补这些运行事实：

- 固定配置在哪里；单机/多机 GBS、本次步数上限与完整 schedule、保存周期、结束保存行为及输出目录。
- 首次短跑的准确命令与是否保存；完整训练命令与短跑区分。
- 初始化大致行为、在哪里看日志/退出码、什么算成功。长跑另写实际执行端、脱离本地会话的方式、计划结束条件和结果位置；说明状态记录是否持续采集，自动通知只有实际配置后才能承诺。
- 停止命令、作用范围、是否保存、连接失败时哪些节点未确认停止。
- 当前性能若需展示：统计窗口、时间边界、配置及波动；不要只贴一个 s/it。
- 已验证与待验收项，尤其新镜像训练、长时稳定、保存恢复和模型效果。长跑完成后写实际步数/时间、各节点退出状态、资源释放、保存点和检查深度；结构核验通过而未恢复时明确分开，不能沿用“仍在运行”或写成完整 schedule 通过。

## 交付审查

按命令出现顺序走读，检查每一步的前提是否已满足：文件是否存在、变量在哪里定义、在哪个用户/机器运行、是否依赖开发者 SSH key 或旧 shell export。配置默认值与文档必须一致。

将验收绑定到最终 commit、部署内容和镜像 digest。入口清理、PR 合入或环境打包后，选择受影响层级复核；不能用旧入口测试证明新入口通过，也不必为纯文字修正重复训练。

用户手动照抄失败时，先核对实际入口版本、身份和部署内容，再修正文档/代码。不要让用户通过越来越长的一串临时 export 去弥补默认入口错误。

当前稿与历史稿分开。权威状态只在一处维护，其他文档引用它；不要在同一文档同时写“已合入”和“尚未提交”。线上稿不能读取时标记“引用用户提供链接，内容未独立核对”，继续依据可读证据整理 review 稿，不修改线上稿。

## 源码修改总结（按需）

单个优化PR内容较多或用户要求单独交付时，总览只保留修改概览与PR索引，另写该PR简稿：生效位置与原理、对应提交、默认/可选/关闭方法、同口径测量和实际验证版本/拓扑。正常训练默认与有界性能复测配置分开；不将实验历史或机器私有信息搬入对外主稿。按需拆分，不要求每个PR额外生成文档。

用于用户要求的源码改动说明，与操作稿、内部复盘各有用途；不要求每个项目都额外生成。已有 review 格式优先，否则采用以下三部分：

1. **修改概览与对应提交**：简表使用“修改范围 | 主要内容 | commit / PR”，每项一句话说明结果，不展开文件清单、函数细节或全部调优参数。初始直接提交可只列 commit，后续修改关联最终保留代码的 PR。
2. **优化项与实测收益**：单列“优化项 | 对照条件与测量层级 | 优化前后 | 收益 | 对应 PR”。区分平台适配、工程功能和性能优化；有可比实测才填收益，无独立测量不编造数字。保留计时窗口、GBS、重复结果等理解数据必需的信息；微基准与整步收益分别标注，百分比不累加。
3. **功能与稳定性验证**：概述实际完成的单机/多机短跑、长跑步数与时长、节点退出及 checkpoint 检查深度。结论对应实际执行版本，不把保存或结构核验写成恢复通过。

写入前核对仓库实际 commit、PR base/head、合入及 revert 状态，避免沿用旧文档的“未合入”。实现与默认配置在不同 PR 时分别对应，例如对齐逻辑由一个 PR 引入、默认启用由后续 PR 完成；不要把某个优化阶段的测试写成后续 PR 已重新训练。当前合入版本与测试版本分别标识。

对外简稿默认链接接收方可访问的源码仓库、commit 和 PR；详细性能证据留在项目记录或适合该受众的附件，不默认链接内部报告和开发机路径。未纳入交付的可选补丁、已放弃方案及排查过程不进入主要改动清单。省去泛泛的风险或 review 待办章节，用准确、积极的表述呈现成果；影响客户复现、数据语义或验收判断的必要范围在对应项简述，精简措辞不改变事实或扩大已验证能力。

将 review 经验同步到通用 skill 时提炼上述写法与核对规则；具体项目的 PR 编号、机器、版本、性能数值和当前运行状态仍保存在项目记录中。
