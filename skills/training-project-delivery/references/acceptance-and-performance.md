# 验收与性能口径

用于定义交付完成条件、审查历史性能或设计复跑。以下是证据层级，不是每个小任务都要重跑的清单。

## 把结论限制在证据覆盖范围

| 验收项 | 最低证据 | 不能替代 |
| --- | --- | --- |
| 环境可用 | 实际解释器、导入路径、版本、设备与目标后端 | 完整训练 |
| 算子/适配正确 | 真实 shape/dtype 的输出、梯度，相关参数更新/边界测试 | 全模型轨迹、收敛 |
| 单机/多机短跑 | 目标配置、optimizer step 数、有限指标、所有工作进程正常完成 | 长期稳定、模型效果 |
| 性能改善 | 相同计时边界、配置、数据与拓扑下的受控 A/B，重复与波动 | 跨口径或跨平台胜负 |
| 长跑稳定 | 实际训练时间区间、持续推进的 step、采集覆盖范围、资源趋势和异常记录 | 启动成功、已等待一晚或未覆盖时长的保证 |
| checkpoint 保存 | 目标模型的完成标记/日志、所需 rank/分片齐全、无保存错误 | 目录存在、小模型测试或恢复能力 |
| checkpoint 恢复 | 独立加载完整 checkpoint，核对步数及所需状态恢复并继续更新 | 仅保存成功或仅加载模型权重 |
| 可迁移交付 | 新建环境按交付命令走通目标级别 | 老容器成功 |
| 制品发布 | 仓库 manifest/digest 与目标制品对应 | 新制品训练已验收 |

本地测试、远端 CPU 冒烟、GPU 训练分别记载。无 GPU 的测试不得写成单机/多机训练验证。不要把同一运行的多个 rank 当作多个独立重复实验。

## 每次性能运行要能回答的问题

- 谁在跑：run ID、时间、机器/GPU、其他占用、源码 commit 与部署哈希、环境/镜像。
- 跑什么：模型/数据版本及插件、抽样/stride、输入 shape、精度、attention、优化器、并行与重计算。
- 有多少工作：micro batch、梯度累积、数据并行规模、GBS、schedule、warmup、实际 optimizer steps。
- 怎么测：预定稳态窗口、起止位置、时钟/同步方式、是否包含取数据/保存/初始化、是否开 profiler。
- 测到了什么：均值、中位数、尾延迟、吞吐、显存、数值/退出状态，及所有未删减的原始计时证据。

对常见等长数据并行：`GBS = 每个 DP rank 的 micro batch × 梯度累积 × DP world size`。存在 TP/PP/EP 等时不能直接乘总卡数；变长样本还需固定或报告有效 tokens/frames，单纯 samples/s 可能不可比。

## 明确三种时间

1. **训练内部时间**：框架计时包围的 train_step；查代码确认是否同步、是否包含优化器和数据等待。变量叫 total 不意味着完整 step。
2. **稳态端到端时间**：固定窗口完成训练步的 wall time，包括该窗口的取数/CPU/通信等待。异步设备计时须定义完成边界，必要的同步方式在 A/B 中保持一致。
3. **作业周转时间**：命令启动到退出，包含模型/数据初始化、编译、保存和清理；它不能与去预热后的 step time 混用。

进度条的 `s/it` 通常是平滑值，仅适合观察；最终均值也不必然等于预定稳态窗口。若只能使用日志，在两条完整 step 时间戳之间计算 `时间差 / 已完成 optimizer step 差`，注明时间戳精度和边界，避免将 micro-step 当 optimizer step。

预先固定 warmup 和统计窗口。保留窗口内慢步，另外解释 DataLoader/保存停顿，不事后择优剔除。分别报告“常规训练窗口”和“含 checkpoint 的运维周期”可帮助规划长跑，但两者不能无标记地替换。

## 扩展效率

设小规模使用 N 张卡，大规模 kN 张卡，测得吞吐为 Q_small、Q_large：

```text
吞吐加速比 = Q_large / Q_small
扩展效率   = Q_large / (k × Q_small)
```

- 弱扩展：每卡工作相同，GBS_large = k × GBS_small，且样本工作量一致时，效率为 `T_small / T_large`。
- 强扩展：GBS 固定，效率为 `T_small / (k × T_large)`。
- 如模型并行策略或有效工作量变化，先解释其比较合同，不套用简化式。

例如单机 GBS64、双机 GBS128 时，不能只看双机每步更慢就判断吞吐退步。反之也不能把 GBS 翻倍的吞吐提升全部归于某一个代码优化。

接近阈值时使用时间相近的配对或交错 A/B，报告每一轮。若展示“各自最佳值比”“每轮效率均值”或“时间均值之比”，必须写清算法；它们可能不同。没有重复测量不能声称稳定达到目标。

## 从现象到可采纳优化

依次建立证据：实际 backend → 模块耗时 → 同条件 A/B → 最终组合复跑。一次改一个主要变量，组合改变时不将整体收益拆给每个变量。

- SDPA/flash：检查实际 forward/backward kernel、mask、layout、cast 和 fallback；第三方包存在不是后端命中的证据。
- 通信：使用真实 message size、dtype、collective、拓扑；channels 和对齐先微基准，再检查训练整体与参数更新/恢复语义。
- 数据：测 `DataLoader.next` 等待、CPU/解码、缓存冷热与 NFS 尾延迟；workers 数按每 rank 生效，合计资源压力必须纳入。
- overlap：检查 timeline 是否真的隐藏关键路径通信，而非把等待搬到后面或挤占计算资源。

专项细节交给性能 skill。通信暴露低而取数尾延迟高时，继续只调 channels 的收益可能有限；这仍是当前证据下的判断，不是硬件上限证明。

## 长跑观察与恢复

根据用户授权的步数或时长预算启动，不因“长跑”推断可无限占卡。区分本次运行上限与学习率 schedule 的总步数，确认按步数自然结束或按约定时长停止；估算耗时不是自行新增定时强停的授权。检查活跃 run 的 PID/环境和日志目录，避免读取旧日志。报告“启动至今”和“首个训练 step 至今”时区分初始化时间。

观察 step 增长、最后更新时间、loss/梯度、显存、CPU/DataLoader、磁盘/cache 和所有节点退出状态。仅 rank0 打进度可能正常；某个 rank 提前退出比其他 rank 随后的 collective timeout 更接近根因。

无人值守观察记录应包含采集时间、最后成功采集时间、间隔与缺失区间；记录进程存活不代表采集成功。无指标、解析失败或节点不可达记为“未知/需复核”，不能将空集合的“全部有限”、未匹配到错误关键词或观察脚本 exit0 当作训练通过。自动汇总须核对目标步数/时间覆盖及训练各节点结果；资源曲线、保存完成与恢复能力分别判定。

无新 step 先对照初始化、编译、数据等待、checkpoint 写入和进程状态，不能仅凭超时推断死锁。若已授权与其他任务共享 GPU，记录共用和争抢对性能比较的影响；不能因此停止他人进程，也不把受干扰结果作为独占基线。

启动前说明 checkpoint 周期与结束保存行为；预计运行量小于保存间隔时，用户可能得不到可恢复产物。中断是否保存须由实现确认，不能口头保证。保存验收核对完成日志、所需 rank/分片文件及错误记录；临时目录、部分分片或写入中不能标为保存通过。人工停止单列为“主动中断”：实际停止原因须与信号/退出码对应，不能把全部非零退出自动归为训练故障，也不能将中断写成完整计划通过。

恢复在独立运行中按项目入口执行，绑定 checkpoint 来源 run/step、源码、环境和并行拓扑，不覆盖原 checkpoint 或已有结果。完整恢复至少核对模型、优化器、调度器、step，以及项目承诺需要恢复的 RNG/数据进度，确认继续更新；只加载模型权重记为权重初始化。拓扑变化须单独验证格式和重分片支持；加载成功不等于续训等价。
