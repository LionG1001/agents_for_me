# 本地 Git 与远端执行

把源码管理和执行环境分开：在本地阅读、修改、Review 和维护正式 Git 历史；把已 Review 的明确文件单向同步到可重建的远端工作区执行验证。

## 先确认规则和权威关系

- 先读取当前项目的 `AGENTS.md` 和用户本轮指令。它们优先于本 Skill；不要用本 Skill 自动覆盖既有项目规则。
- 本地源码仓库是正式代码的第一事实源，也是唯一正式 Git 管理位置。
- 远端执行工作区只用于编译、运行、Profile、训练和测试；日常流程中不在该工作区 branch、commit、pull、push 或 reset。
- 区分远端执行工作区与 GitHub、GitLab 等代码托管平台。只有本地 Git 可以按项目权限向代码托管平台 push。
- 默认只在本地修改正式源码，并将最小文件范围单向同步到远端。
- Git 记录代码实际发生了什么；任务记录说明为什么修改、如何验证，以及为什么保留、继续或回退。
- 一个可独立解释和回退的逻辑实验形成一个 Checkpoint。Checkpoint 是 Review 和决策点，不等于每次都 commit。
- 只有与最终 diff 对应、完成所需验证的稳定修改才可进入正式本地 commit。

如果当前项目采用“远端写入、本地 Review”、远端 Git 是正式历史或其他相反模式，停止套用本 Skill，遵循当前项目规则。

## 建立项目身份

在修改、同步或远端执行前，从用户提供的信息和现场只读核验中确认：

- 项目名称、任务目标和允许修改范围
- 唯一本地项目根目录、源码仓库边界，以及是否存在外层工作区与内层源码仓库
- 本地基线 branch 与 commit、当前分支、工作树状态和既有修改
- 代码托管平台与 branch、commit、push、MR/PR 权限
- 远端连接方式、主机、账号、容器或 Pod、Namespace、镜像
- 远端同步路径与容器/Pod 内实际运行路径
- 默认排除的数据、模型、日志、缓存、checkpoint 和构建产物
- 实际构建/测试命令、GPU/数据/时长范围及最后核验时间

主机、账号、容器、Pod、路径、分支、commit、镜像和命令不得猜测。身份不一致或关键值无法只读确认时，先报告差异；需要该值才能继续的写操作必须暂停。

创建或更新项目级 `AGENTS.md`、复杂任务记录或最终交接时，读取 [项目与实验记录模板](references/project-record-templates.md)。使用当前真实值替换模板字段，删除项目不需要的段落；不要让历史值与当前权威值并列。

## 建立首次本地基线

代码最初只在远端时：

1. 只读确认来源、分支、commit 和工作树状态。远端存在 `.git` 时，可读取 `git remote -v`、`git branch --show-current`、`git rev-parse HEAD` 和 `git status --short` 作为来源证据。
2. 排除数据、模型、日志、缓存和构建产物，将原始源码带到本地。
3. 区分项目既有修改、本次任务修改和生成产物。
4. 经项目权限允许后，在本地建立明确的 baseline commit。
5. 此后将本地 Git 作为正式历史，默认只从本地同步到远端。

来源不清或既有修改无法归属时停止，请用户确认基线。

普通项目使用单一本地仓库。需要把规则、实验和生产源码分开时，可以使用外层工作区仓库加内层源码仓库；外层记录必须引用内层源码 commit，且外层 commit 不得被描述为已经包含被忽略的内层源码修改。

若项目权限允许，任务默认在本地任务分支进行，不直接修改公共主分支。创建分支前核对工作目录、仓库根、当前分支、HEAD 和工作树；分支名优先遵循项目规则，否则可用 `codex/<日期>-<任务关键词>`。

## 推进一个逻辑实验

每一轮遵循以下闭环：

1. 确认本地/远端身份、基线和既有修改。
2. 声明实验 ID、问题与证据、当前假设、计划修改的文件和 symbols、选择原因、风险以及验证上限。
3. 只在本地修改正式源码，不扩大已声明范围。
4. Review 本地 diff 并形成 Checkpoint。
5. 预览并执行本地到远端的最小同步。
6. 在已授权的环境、机器、GPU、数据和时长范围内执行远端验证。
7. 根据证据决定保留、继续或回退。
8. Review 与最后一次远端验证对应的最终代码；获得相应 Git 权限后，才创建本地 commit。
9. 更新必要记录并完成交接。

假设变化、准备扩大文件范围、一个独立问题已定位、准备同步或高成本测试、准备 commit/交接，或者 diff 已经大到难以一次 Review 时，先形成 Checkpoint。

## Review 本地 Checkpoint

修改后先看整个工作树，再只检查本次明确文件：

```bash
git status --short
git diff --check -- <本次文件...>
git diff --stat -- <本次文件...>
git diff -- <本次文件...>
```

逐文件说明改动的 symbols、实际变化和原因，并明确与原计划的差异、本地检查结果、尚未验证内容和准备同步的文件。不得把任务开始前已有的未提交修改计入本次成果。用函数、类、算子或配置 key 作为稳定定位；行号只能辅助说明。

## 最小化同步到远端

只同步已 Review 的明确文件。生成相对于本地项目根目录的文件清单，先 dry-run：

```bash
rsync -an --itemize-changes \
  -e "ssh -p <SSH_PORT>" \
  --files-from="<SYNC_FILE_LIST>" \
  "<LOCAL_PROJECT_ROOT>/" \
  "<SSH_USER>@<SSH_HOST>:<REMOTE_SYNC_ROOT>/"
```

检查预览只包含允许范围后，才去掉 `-n` 正式同步。

- 不同步 `.git/`、凭据、数据、模型、checkpoint、日志、缓存或构建产物。
- 不默认使用 `--delete`、`--delete-excluded` 或整目录强制覆盖。
- Docker bind mount 只同步到唯一宿主机挂载源；共享存储只复制一次。
- Kubernetes Pod/容器名可能变化，操作前重新确认 Namespace、Running 和 Ready。
- 远端目标文件存在来源不明的源码差异时停止，不直接覆盖。
- 同步后用再次 dry-run、关键文件 SHA256 或部署 manifest 至少确认一种一致性证据。

每次远端验证都必须关联“实验 ID + 本地基线 commit + 同步文件清单”。性能、精度、长时间或高成本测试还应保留文件哈希或部署 manifest。

## 执行远端验证并收集证据

测试前确认实际主机、容器/Pod、镜像、运行路径、GPU 和关键依赖。记录构建与测试命令、退出码、日志位置、性能/精度/正确性结果，以及哪些步骤已执行、已验证或未执行。

进程启动、GPU 占用、输出目录生成、forward 成功或单步完成都不能自动证明完整任务成功。正式训练、多机多卡、全卡压力测试、长时间任务，或扩大机器、数据、网络和时长范围，需要用户明确授权。

## 根据证据决策

### 保留

清除临时诊断代码和无关文件。如果待提交代码发生变化，重新同步并按影响范围重新验证；不得沿用清理前版本的测试结论。Review 最终 diff，确认它与最后一次远端验证对应，再根据 Git 权限提交。

### 继续

记录新观察和原假设是否成立，更新下一轮假设，在同一任务分支继续。将状态表述为仍在实验，不得宣称已完成。

### 回退

先保存必要失败证据，只回退本次实验修改，不破坏任务开始前已有内容。未核对工作树时不得执行 `git reset --hard`。

## 维护正式 Git 历史

提交前 Review 整体状态，只暂存明确文件；默认不使用 `git add .` 或 `git add -A`。commit message 应说明问题、实际修改、方案原因，以及远端验证的环境、命令和结果。commit、push 和 MR/PR 均以项目授权为前提。

简单任务保留 Checkpoint 汇报、Git diff、commit message 和最终交接即可。跨多天、多轮实验、性能优化或需要交接的复杂任务，使用 `GOAL.md` 或 `TASKS/<task-id>.md`；格式见记录模板。失败实验只有在对后续有复用价值时才进入正式记录。

## 处理远端临时修改例外

只有调试工具或环境限制导致最小诊断必须在远端完成时，才允许远端临时实验：先说明原因和文件范围，保存修改前后 diff/补丁，把有效修改带回本地重新应用和 Review，再从本地重新同步并验证。远端临时版本不得长期领先于本地，也不得与本地同时修改同一文件；最终代码仍只由本地 Git 记录。

## 必须停止并报告

遇到以下任一情况，不继续自动修改或同步：

- 仓库、分支、基线、主机、容器/Pod、镜像、挂载或路径不一致
- 目标文件有无法归属的修改，或者本地和远端同时修改
- 同步预览超出允许范围，或操作需要删除未知文件
- 需要扩大代码、机器、GPU、数据、时长、网络或测试范围
- 凭据、模型、数据、日志或 checkpoint 可能进入 Git
- 需要修改驱动、基础镜像、关键依赖或公共接口但未获授权
- 测试失败且原因不明，继续修改只会扩大不确定性

报告观察、影响、已完成项、未完成项、所需确认和最安全的下一步。任务结束时明确区分“已修改”“已同步”“已执行”“已验证”和“仍待确认”。
