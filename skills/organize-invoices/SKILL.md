# 发票整理

按出差日期整理餐饮补助发票，同时保护唯一原件并保证结果可追溯。

## 首次日期要求

首次整理前必须取得精确的开始和结束日期，格式为 `YYYY-MM-DD`。用户已经给出两个日期时，确认后直接执行，不要重复询问。用户明确要求“重新整理”且未改变范围时，沿用上一轮范围。

## 安全底线

1. 每个唯一发票号码必须在 `原始发票/` 中保留一份字节不变的权威原件。不得删除或覆盖唯一原件。
2. 只能按发票号码判断重复，不能按文件名或金额判断。确认号码和关键字段一致后，只保留一份权威原件；删除重复原件后报告删除对象及可恢复性。
3. 日期结果目录中的 PDF 是从权威原件复制的工作副本，不得反向修改原件。
4. 交通发票不得计入餐饮补助。
5. 不得修改超额票原件。用户未明确批准超额计入规则时，不得自动拆分或部分申报；用户已批准时，只调整台账计入额或跨日分摊，PDF 保持字节不变。
6. 如果历史操作导致只有结果副本、没有 `原始发票/`，必须先从每个唯一发票号码的现存副本重建原件档案，并核验哈希，再替换结果。

改变发票文件前，完整阅读 [references/rules.md](references/rules.md)。

## 操作流程

### 1. 只读盘点

- 查找 `未整理/`、`原始发票/`、`交通/` 和已有结果目录。
- 处理 PDF 时，遵循可用的 PDF 技能完成文本提取与票面核验。
- 在已安装 `pdfplumber` 时运行只读盘点脚本：

```powershell
python scripts/invoice_inventory.py "原始发票" --json
```

- 分别盘点 `原始发票/` 和 `未整理/`；不要把结果工作副本当成重复原件。需要检查整个工作区时，必须按目录角色解释有意生成的工作副本。
- 提取发票号码、开票日期、价税合计、购销方、类别和文件哈希。
- 对新增文件、字段不明确或分类有疑问的 PDF 进行渲染和视觉核验。
- PDF 加密、无文本层或解析失败时，按 PDF 技能进行渲染/OCR；仍不能可靠识别时转人工复核，不得猜测号码或金额。

### 2. 建立和维护原件档案

- 不存在时创建 `原始发票/`。
- 如果原件档案为空但结果目录已有唯一 PDF，先把每个唯一号码的一份现存 PDF 原样复制到 `原始发票/`，核验哈希一致后再重排结果。
- 将 `未整理/` 中每张唯一新增原件移动到 `原始发票/`，不得重写文件。
- 交通原件也必须进入 `原始发票/`；`交通/` 只保存可选工作副本。
- 同号来票须核对号码、日期、金额、购销方等关键字段，并优先比较哈希。关键字段冲突时停止自动去重，转人工复核。
- 原件文件名冲突但发票号码不同或未知时不得覆盖；使用发票号码前缀生成稳定名称，不能可靠识别号码时转人工复核。

### 3. 分类

- 默认纳入饭店、餐费、餐饮服务、合规外卖食品、包装费和餐饮配送费。
- 只有项目行或关联证据能证明属于餐食/外卖配送时，才纳入配送费；普通物流转人工复核。
- 完全排除交通发票的餐补分配。
- 未取得明确超额处理口径时，单张金额高于每日限额的发票只复制到 `超150元待单独处理/`。
- 非餐饮、购方不符、字段不可读或分类不确定的发票转人工复核。

### 4. 超额票处理

- 用户批准“刚刚超过按上限计算”时，票面金额略高于每日限额的票按每日上限计入，原件和工作副本不得改写；台账同时记录票面金额和计入金额。
- 用户批准“大额票连续几天平均且可含周末”时，用 `ceil(票面金额 / 每日上限)` 得到最少连续自然日数，按票面金额平均分摊。分摊到分时，最后一天调整 0.01 元以内的尾差，确保总计等于票面金额。
- 跨日区间必须位于出差范围内，并满足用户给出的开票日期方向约束。只有跨日大额票可以启用周末日期；普通票仍只分配到工作日。
- 大额票只在 `跨日平均发票/<开始>至<结束>/` 保存一份工作副本，不在每日目录重复复制。台账只保留一条发票主记录，清单列出每日分摊明细。
- “略超”和“大额”的数值边界未明确时，只对明显无歧义的票自动分类；边界附近转人工复核。本技能当前示例口径中，152.00 元相对 150.00 元属于略超，497.01 元属于大额。

### 5. 组合优化

- 默认只计算所给范围内的周一至周五；用户提供其他工作日口径时服从用户。
- 每日金额不得超过限额，默认 `150.00` 元。
- 允许工作日完全没有发票。
- 读取 `已报销发票台账.csv`。新周期必须排除已最终报销的号码；同一日期范围重新整理时，先撤销活动结果对应的临时分配，再重新计算。
- 用户要求最大化收益时，按以下顺序优化，前一目标优先于后一目标：
  1. 最大化本轮可报销计入总额。
  2. 最大化正好达到每日限额的日期数。
  3. 最大化其余接近限额的日期数。
  4. 让开票日期尽可能贴近分配日期。
  5. 其他目标相同时，优先使用较少文件。
- 用户未给容差时，把 `148.00–150.00` 元视为接近限额，并在结果中说明。
- 从 `原始发票/` 复制入选发票到日期目录。
- 不为消耗发票而创建低金额日期。未入选的合规发票复制到 `下一次报销待整理/`。
- 普通票同一发票号码不得分配两次；跨日大额票只能有一条主记录和一份工作副本，逐日分摊不是重复用票。

重新整理时，把同日期范围编号最大的结果视为活动结果，除非用户另有指定。默认将活动结果更名为下一编号并原地重排其工作副本；不要同时留下两套活动 PDF。历史结果默认只保留清单。完成后更新 `已报销发票台账.csv`，记录发票号码、报销范围、分配日期、金额和状态。

### 6. 交付前核验

- 从结果 PDF 重新提取金额和发票号码。
- 确认没有工作日超过限额，结果内部没有重复号码。
- 确认每个结果副本都能映射到 `原始发票/` 中的同号原件；预期字节一致时核验哈希。
- 确认权威原件集合除已核实的重复原件外没有减少。
- 确认交通票未进入餐饮日期目录，超限额和结转目录内容正确。
- 对略超票核对票面金额与计入上限；对跨日票核对连续日期、周末权限、每日分摊尾差和票面总额，并确认同号 PDF 只保存一份跨日工作副本。
- 确认本轮号码未与其他已最终报销周期的台账记录冲突。
- 对新增或存在疑问的 PDF 进行最终渲染核验。

### 7. 汇报

在结果目录生成 `整理清单.md`，并向用户报告：

- 已填日期、金额与缺口；
- 没有发票的日期；
- 当前周期总缺口；
- `下一次报销待整理/` 中的发票；
- `超150元待单独处理/` 中的发票；
- 略超票的票面金额和按上限计入金额；跨日平均票的日期范围、日均额、逐日分摊和周末日期；
- 排除的交通票、无效票或待复核票；
- 删除的重复票和原件保留状态；
- 工作日、容差和日期匹配假设。

总缺口默认按 `工作日数量 × 每日上限 - 本轮全部计入总额` 计算；跨日票的周末分摊计入本轮总额，但不增加工作日理论额度。用户另有总额度口径时服从用户。

如果全部日期已覆盖，或现有合规票无法继续补缺且只剩超限额票，明确提示用户进行人工处理。
